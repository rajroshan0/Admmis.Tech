## 2. Locale scheme (confirmed)

Sudip, Neha and Hritik all assumed this scheme. I checked it against the alternatives and keep it.

| Option | Verdict |
|---|---|
| **A. EN unprefixed, NE `/ne/`** | **Chosen.** URLs in the sitemap, on print material and at the opening event (`tech.admmis.org/opening-event`) stay short. EN, the launch language and `x-default`, has the cleanest URLs. Adding NE adds URLs; no EN URL changes |
| B. Always prefixed (`/en/`, `/ne/`) | Symmetric and simpler routing, but all printed and shared EN URLs gain `/en`. Rejected |
| C. Sub-domains (`ne.tech.admmis.org`) | New DNS, certificate and Cloudflare config; splits authority. Rejected |
| D. Domain per country, or Accept-Language auto-redirect | Rejected: duplicate-content and cache problems; ADR-015 fixes one host |

**Slugs.** One English slug per document in both locales (sitemap rule 3, content-model `slug` not localized). Nepali SEO does not require Devanagari slugs; Latin slugs are shorter, copyable and never need percent-encoding in links shared on chat apps. Revisit only if Nepali keyword research (Feb) shows a measurable case.

**Notification to others:** scheme unchanged, so no one needs to change anything. The one new fact for Sudip and Neha is §6 (`translatedLocales`).

### 2.1 URL behaviour (what the router must do)

`ENABLED_LOCALES=en` at launch.

| Request | Result |
|---|---|
| `/services` | 200, EN page |
| `/en/services` | 308 to `/services` |
| `/ne/services` | 404 (locale disabled) until switch-on |
| `/ne/services` after switch-on | 200 NE page (or the untranslated rule, §6) |
| `/services/` (trailing slash) | 308 to `/services` (Next default; URL rule 1) |
| `/NE/services`, `/Services` | not matched, 404 (lowercase only, URL rule 1) |
| `/xx/services` | 404 |
| `/` with `Accept-Language: ne` | 200 EN. **No detection redirect** |
| `/services?utm_source=x` | 200, canonical `/services` |
| `/api/*`, `/admin/*`, `/_next/*`, files with an extension | bypass the locale routing (matcher) |

Reasons for no detection: a redirect by header or cookie would vary the response by visitor, break CDN caching, hide EN pages from crawlers (which send no language preference, or EN) and make `x-default` meaningless. The visitor chooses with the switcher; the choice is just a link.

### 2.2 Routing implementation

- `src/lib/i18n/config.ts`: `ALL_LOCALES = ['en','ne']`, `DEFAULT_LOCALE = 'en'`, `enabledLocales` parsed from `ENABLED_LOCALES` by `lib/env.ts` (Hritik added it to the env list). It is a **deploy-time** setting because it feeds `generateStaticParams`. It reaches client islands through props, not a public env var.
- `src/lib/i18n/routing.ts`: `defineRouting({ locales: enabledLocales, defaultLocale: 'en', localePrefix: 'as-needed', localeDetection: false })`, shared by the proxy, `Link`, `redirect` and the path helpers.
- Proxy (the routing file; its Next 16 name, `proxy.ts` vs `middleware.ts`, is **verify at scaffold**): runs next-intl's handler; matcher excludes `api`, `admin`, `_next`, files with an extension, and `preview`.
- `src/app/(site)/[locale]/layout.tsx`: validates `locale` against `enabledLocales` (`dynamicParams = false` on the segment), calls `setRequestLocale(locale)` so the page stays static, sets `<html lang>`.
- Every `(site)` layout and page calls `setRequestLocale` and uses no `cookies()`, `headers()`, `draftMode()` or `searchParams` (T-301 §7; CI enforces static output, `docs/ci-spec.md` §9).
- Own helpers in `src/lib/routes/`: `pathFor(locale, path)` (adds `/ne` when needed), `alternates(path, translatedLocales)`. All internal links go through them or through next-intl's `Link`. A lint rule forbids hard-coded `href="/…"` strings in templates (Hritik to confirm the rule).
- next-intl can also emit alternate-link headers. **Turned off** (`alternateLinks: false`): we emit `hreflang` ourselves from `translatedLocales` (§6), so a partly translated page never advertises a language that is not ready.

### 2.3 Library choice and reasons

| | next-intl | Hand-rolled (proxy rewrite + JSON loader + `Intl` helpers) | i18next family |
|---|---|---|---|
| App Router and RSC support | built for it | we write it | adapter needed |
| `as-needed` prefix | built in | we write it | not built in |
| Static rendering | `setRequestLocale` | we write it | partial |
| Plurals, ICU messages | yes | we write it | yes (other syntax) |
| Typed message keys | yes (declaration merging) | we write it | partial |
| Client JS | small if namespaces are scoped | smallest | larger |
| Maintenance risk | one dependency | our code forever | one dependency |

Chosen: **next-intl**, because the scheme is exactly its `as-needed` mode and it saves us owning plural and format code. Risks and controls:
1. Client bundle: Server Components use the server API (`getTranslations`); only the namespaces an island needs are passed to `NextIntlClientProvider` (`forms`, `nav` for the menu, `consent`). Cost is measured with the bundle analyzer at scaffold against the 150 KB budget. If it fails, the fallback is passing pre-resolved strings as props to islands, with no provider on content pages.
2. Behaviour in Next 16 (proxy file, static rendering): smoke-tested at scaffold (T-103). If it fails, the hand-rolled route remains possible because the helpers in §2.2 hide the library behind `lib/i18n` and `lib/routes`.
3. Version: unpinned here; Hritik pins at scaffold (`docs/scaffold-plan.md` lists 4.14.9).

## 3. Messages (UI strings)

### 3.1 What goes where

| Kind | Where | Examples |
|---|---|---|
| Page content, titles, SEO, nav labels, footer, contacts, cookie banner copy, thank-you text | **CMS** (localized fields, `siteSettings`) | everything an editor changes |
| Fixed UI text of components and forms | **messages** | form labels, placeholders, validation errors, button text, aria-labels, "skip to content", breadcrumb label, 404/500 text, currency toggle, "Read more", date relative words |
| Option labels (size band, budget range, industry) | **messages** (keys in `src/config/*.ts`, content-model §3.18) | `forms.sizeBand.S` |
| Prices and amounts | **never text**: `Intl` from `pricing` minor units | — |
| Internal alerts to sales (email, chat) | English only, not localized (leads.md §8) | — |

Rule: no user-facing literal in `.ts`/`.tsx` (lint rule `no-literal-strings` or equivalent in JSX, Hritik to choose at scaffold; allowed: `className`, test ids, enum keys).

### 3.2 Layout

```
src/messages/
  en/
    common.json      # buttons, skip link, breadcrumb, language names, generic labels
    nav.json         # aria labels, menu toggle text (menu items come from CMS)
    forms.json       # labels, hints, errors, success/failure, WhatsApp fallback text, option labels
    errors.json      # 404, 500, rate-limited, offline
    consent.json     # only strings not editable in CMS (button states, aria)
    pricing.json     # table headers, "from", "per month", "quote only", currency names
    seo.json         # templated parts only (e.g. breadcrumb root "Home"), not page titles
  ne/                # same files, same keys (created at switch-on preparation)
```

- One namespace per file; file name = namespace; keys are nested, lowercase `dot.case` paths, English-descriptive (`forms.errors.email_invalid`), never the English sentence.
- **Keys are the contract with the API:** `leads.md` returns keys such as `leads.error.validation_failed` and `leads.field.email_invalid`; they live in `forms.json` under `leads.*`. Neha adds new API keys and tells me; CI checks every key the schema and API can emit exists in `en`.
- ICU syntax for plurals and variables (`{count, plural, one {# project} other {# projects}}`). No string concatenation to build sentences. No HTML in messages; for links or emphasis, use rich-text placeholders (`<link>…</link>`) mapped to components.
- Dates, numbers, currencies are never formatted inside messages by hand; pass values and use the formatters (§8).
- A short context comment is not possible in JSON, so each namespace has a sibling `_notes` key (ignored at runtime) for translators when the meaning is not obvious.

### 3.3 Loader and fallback

`src/lib/i18n/request.ts` (next-intl request config): loads `en/*.json` as the base, then deep-merges `<locale>/*.json` over it. A missing NE key therefore renders the EN string. In development a missing key logs a warning; in production it is silent for the visitor and counted in the build report.

Gate before NE is enabled: `pnpm test` includes `messages.test.ts`: (a) every `ne` key exists in `en` (no orphan), (b) **for switch-on**, every `en` key has a non-empty `ne` value; the second check is skipped while `ENABLED_LOCALES` has no `ne` and required when it does. ICU placeholders in `ne` must match `en` (same variable names).

## 4. CMS localization (what already exists, and how the frontend uses it)

From content-model §1: every public text field is `localized: true`; blocks and arrays are shared structure with localized text inside; `slug` is not localized; fallback `ne` empty → `en`; admin UI stays English.

Frontend rules:
1. Data functions take `locale` and return one flat resolved language (fallback applied inside the data layer, never in components).
2. A page is never built from mixed locales for **layout**: the structure is shared, so NE reuses the EN block order exactly.
3. Fields that are localized but meant to stay identical (brand names, product names such as "AI agents") are entered in both locales or left empty to fall back; no special code.
4. Rich text: the Lexical output for the locale; links inside use internal doc references so they are re-prefixed by `pathFor`.
5. Media `alt` is localized; the frontend uses the active locale's alt, falling back to EN.
6. Leads store `locale` (`en`/`ne`) and the form sends it (leads.md §2.1). Alerts to sales stay English.

## 5. Fallback matrix

| Item | Missing in NE | Visitor sees | Search engines get |
|---|---|---|---|
| UI string | key absent | EN string | — |
| CMS text field | empty | EN text | see page rule below |
| Media alt | empty | EN alt | — |
| Whole document (no NE at all) | all fields empty | EN content on `/ne/…` | `noindex`, self canonical, no `hreflang` |
| Document partly translated | some fields empty | mixed | same as above until complete |
| Collection list (blog, jobs) | an item untranslated | item listed with EN text | item URL follows page rule |
| Route/slug | — | same slug, so always resolves | — |

**Page rule (Hritik, 2026-11-06).** A page counts as translated into a locale when `translatedLocales` contains it. `translatedLocales` is a computed field on every localized document (requested from Neha) that holds the locales where all required publish fields (title, SEO title/description, and the document's primary text fields) are non-empty. Until then:
- the NE URL is reachable (editors can review it) but sends `noindex` and a **self-referencing canonical** (not a canonical to EN: noindex plus a canonical to another page is a conflicting signal),
- it is absent from the NE alternates of the EN page (no `hreflang`),
- it is excluded from `sitemap.xml`,
- the language switcher on the EN page still links to it only if the NE page is translated; otherwise the switcher item is hidden for that page.

## 6. SEO: canonical, hreflang, sitemap

| Output | Rule |
|---|---|
| Canonical | absolute, self-referencing per locale; EN `https://tech.admmis.org/x`, NE `https://tech.admmis.org/ne/x` |
| `hreflang` | on each page: one entry per locale in `translatedLocales` (each page lists itself and all its translations) plus `x-default` pointing to the EN URL. With only EN enabled: none emitted |
| `<html lang>` | `en` or `ne` |
| `og:locale` | `en_US`-style value from config (`en` → `en_US`, `ne` → `ne_NP`), `og:locale:alternate` for translated siblings |
| `sitemap.xml` | one `<url>` per locale and page that is indexable and translated, each with `xhtml:link` alternates (Next sitemap `alternates.languages`) |
| `robots.txt` | unchanged by locale. `/ne/…` thank-you page also `noindex` |
| Redirect table | paths stored without locale (content-model `redirects.from`); the lookup runs per locale and keeps the prefix |

Sudip should check `x-default` = EN URL and that Nepali pages can have their own `metaTitle` and keywords (they are localized fields, so yes).

## 7. Typography and Devanagari

All three brand directions support Devanagari (`design/brand-directions/README.md`): Poppins + Hind, Mukta, Noto Serif/Sans with Devanagari. The brand direction is not yet chosen (Gate 1), so the mechanism is specified, not the family.

1. **Font files load per locale.** `src/brands/<brand>/fonts.ts` (Satish) exports `fonts.latin` (all locales; NE pages still need Latin for brand names, numbers and English terms) and `fonts.devanagari` (NE only). The locale layout adds the Devanagari font object only when `locale === 'ne'`. EN pages must not request any Devanagari font file. This is a test (§11), checked in the network panel at scaffold.
2. `next/font`, self-hosted, `display: swap`, subset to what is needed (`latin`, plus `devanagari` for NE), `adjustFontFallback` where available. Fallback stack ends with a system Devanagari font (`"Noto Sans Devanagari"`, `"Nirmala UI"`, `Mangal`, `sans-serif`), so text is readable before the web font arrives.
3. CSS (Satish owns tokens; request sent): `:lang(ne)` sets `--leading-body` about 1.6–1.75 and heading leading at least 1.3 (Devanagari matras and headline strokes need more vertical room than Latin); `letter-spacing: normal` (tracking breaks conjuncts); no `text-transform: uppercase` reliance (no case in Devanagari); no `font-synthesis` bold/italic on Devanagari (use real weights, avoid faux italics).
4. Layout: no fixed-width or fixed-height text boxes; buttons and nav items grow in height; truncation by `line-clamp` only with `title`/full text available; test with long Nepali strings (usually 20–40 percent longer visually than EN; **estimate, verify in the Nepali sample page**).
5. Logical properties (`ms-`, `ps-`, `start`/`end`) everywhere, as in standards §4. No RTL locale is planned; this only keeps the door open.
6. A **Nepali sample page** (hero, service block, pricing table, form with errors, footer) is built in the first template milestone so typography issues show up in November, not in February. Test content is placeholder text marked `TODO(copywriter)`; no real Nepali copy is invented by engineering.

## 8. Formatting dates, numbers, money

All via `Intl` (no date library, standards §10), wrapped in `src/lib/i18n/format.ts` with unit tests: `formatDate`, `formatNumber`, `formatMoney`.

| Item | EN (launch) | NE (Feb) |
|---|---|---|
| Format locale | `en-US` style grouping (`100,000`), matching ADR-012 wording "NPR 100,000/month". **Open: Nepali lakh grouping (`1,00,000`)** | `ne-NP`; numerals **Latin digits by default** (`-u-nu-latn`) |
| Money input | integer minor units and ISO code from `pricing.amounts` | same |
| Money output | `Intl.NumberFormat` with `style: currency` for `USD`; for `NPR` the currency display (`NPR` vs `Rs`) is a config choice (Sudip/Sharwan) | same |
| Dates | stored UTC ISO; displayed in `Asia/Kathmandu` time zone (NPT, UTC+05:45) for events; `dateStyle: 'long'` | same, Gregorian |
| Phone | as entered; WhatsApp links need digits only (`wa.me`) | same |

Defaults chosen so that nothing is guessed in code: format settings sit in `src/brands/<brand>/brand.ts` (`formatLocales: { en: 'en-US', ne: 'ne-NP-u-nu-latn' }`), editable by review, not hard-coded in components. Unit tests cover NPR and USD at both locales, zero, large and minor-unit edge values.

2. Nepali digit grouping (lakh/crore) for NPR prices on NE pages.
3. Bikram Sambat dates. Browsers' `Intl` has no Nepali (BS) calendar. If wanted, it needs a small conversion helper (new dependency, decision needed). Launch shows Gregorian dates only; the opening event is 1 Jan 2027 (Gregorian).

## 9. Language switcher

- Component (Satish) in header and footer; rendered only when `enabledLocales.length > 1`. Until then nothing is rendered (sitemap §4: "NE hidden until ready").
- Each item is a normal link to the same page in the other locale (`pathFor`), built from the page's `translatedLocales`; no JS needed. `lang` attribute on each link (`lang="ne"` with the native name "नेपाली"; name strings come from `common.json`, not code). `aria-current` on the active one.
- Preserves path and drops the query. The visitor's choice is not stored in a cookie (no detection logic reads it; avoids a cookie-consent question).
- Language names appear in their own language ("English", "नेपाली") so a visitor can find their own.
