# Lead API contract and pipeline — ADMMIS.TECH

Owner: neha · Task: T-402 · Version: v0.2 draft · 2026-11-06 · Reviewer: hritik
Binding: ADR-006 (consent), ADR-007 (no lead lost), `docs/standards.md` §3 and §8. Collection fields: `docs/api/content-model.md` §3.16–3.17.
Unknowns are `TODO(roshan)`: team chat tool, sales email, CRM (Q10, due 20 Nov), retention period, IP-hash salt rotation.

## 1. Guarantee

Once `POST /api/leads` returns `201`, the lead is committed in PostgreSQL together with its delivery jobs, in **one transaction**. Email, chat, CRM and Turnstile outages cannot remove it. If the database cannot commit, the API returns `503` and the form keeps the visitor's data and shows the WhatsApp/phone fallback; the lead is never acknowledged without being stored.

## 2. Endpoint

`POST /api/leads` · `Content-Type: application/json` · max body 16 KB · no auth · same-origin only.
Route file: `src/app/api/leads/route.ts` (Neha). Schema file: `src/lib/schemas/lead.ts` (shared, Neha + Mahendra). Logic: `src/lib/server/leads/*`.
Never cached (`dynamic = 'force-dynamic'`, `Cache-Control: no-store`). Cloudflare bypasses cache for `/api/*` (Raj).

### 2.1 Request body

| Field | Type | Req | Rules |
|---|---|---|---|
| `name` | string | yes | trim, 2–100 chars, no control chars |
| `email` | string | one of email/phone | valid email, ≤254, lowercased |
| `phone` | string | one of email/phone | digits, spaces, `+ - ( )`; 7–20 digits after cleaning; normalised to E.164 if country code present, else stored as given with `locale` hint. Nepal numbers (+977) accepted |
| `company` | string | no | ≤150 |
| `service` | string | no | key of a service (`web-development`, …) or `other`; validated against a config allowlist `src/config/services.ts` (no CMS read on the hot path), pattern `[a-z0-9-]`, max 60 |
| `sizeBand` | enum | no | `S` `M` `L` `XL` (from `src/config/size-bands.ts`) |
| `budgetRange` | string | no | one of config keys (TODO(sudip/roshan), open question) |
| `message` | string | yes for `contact`/`quote`, no otherwise | 10–3000 chars after trim |
| `formKind` | enum | yes | `contact` `quote` `rent` `event` `callback` |
| `pricingKey` | string | no | `pricing.key` if the visitor clicked a plan (e.g. `rent-website-m`) |
| `locale` | enum | yes | `en` (`ne` later) |
| `consent` | object | yes | `{ contact: true, policyVersion: string }`; `contact` must be `true` or the request is rejected |
| `source` | object | no | `{ utmSource, utmMedium, utmCampaign, utmTerm, utmContent }` each ≤100; `referrer` ≤500 (URL); `landingPath` ≤300; `pagePath` ≤300 |
| `turnstileToken` | string | yes | ≤2048 |
| `idempotencyKey` | string | yes | UUID v4 generated by the form when it mounts; reused on retry of the same submission |
| `contact_ref_hp` (`HONEYPOT_FIELD`) | string | honeypot | hidden field, must be empty. Non-empty → silent fake success |

Unknown keys are rejected (`.strict()`). All strings are stripped of `\u0000` and zero-width chars. HTML is not interpreted anywhere; email templates escape values.

```ts
// src/lib/schemas/lead.ts  (reference shape; final code written in week 2)
import { z } from 'zod'

const text = (min: number, max: number) =>
  z.string().trim().min(min).max(max)

export const leadSchema = z
  .object({
    name: text(2, 100),
    email: z.string().trim().toLowerCase().email().max(254).optional(),
    phone: z.string().trim().regex(/^[0-9+()\-\s]{7,25}$/).optional(),
    company: text(1, 150).optional(),
    service: z.string().trim().max(60).optional(),
    sizeBand: z.enum(['S', 'M', 'L', 'XL']).optional(),
    budgetRange: z.string().max(40).optional(),
    message: text(10, 3000).optional(),
    formKind: z.enum(['contact', 'quote', 'rent', 'event', 'callback']),
    pricingKey: z.string().max(80).optional(),
    locale: z.enum(['en', 'ne']),
    consent: z.object({ contact: z.literal(true), policyVersion: z.string().max(40) }),
    source: z
      .object({
        utmSource: z.string().max(100).optional(),
        utmMedium: z.string().max(100).optional(),
        utmCampaign: z.string().max(100).optional(),
        utmTerm: z.string().max(100).optional(),
        utmContent: z.string().max(100).optional(),
        referrer: z.string().max(500).optional(),
        landingPath: z.string().max(300).optional(),
        pagePath: z.string().max(300).optional(),
      })
      .strict()
      .optional(),
    turnstileToken: z.string().min(1).max(2048),
    idempotencyKey: z.string().uuid(),
    contact_ref_hp: z.string().max(0).optional(), // honeypot
  })
  .strict()
  .refine((v) => v.email || v.phone, { path: ['email'], message: 'contact_required' })
  .refine((v) => !['contact', 'quote'].includes(v.formKind) || !!v.message, {
    path: ['message'],
    message: 'message_required',
  })
export type LeadInput = z.infer<typeof leadSchema>
```
The honeypot `contact_ref_hp` is handled before strict parsing so the fake success path works even when the value is non-empty (see step 3). Error messages in the schema are i18n **keys**, never prose (standards §3).

### 2.2 Success response

`201 Created`
```json
{ "ok": true, "leadId": "ld_8f3a…", "next": { "redirect": "/contact/thank-you", "whatsapp": true } }
```
- `leadId` is opaque (public id, not the DB serial). `next.redirect` is a locale-less path; Mahendra adds the locale prefix. `next.whatsapp` tells the thank-you page to show the WhatsApp button.
- Duplicate `idempotencyKey` (retry of an already stored submission): `200 OK` with the **same body** and header `Idempotent-Replay: true`. No second lead, no second notification.
- Honeypot hit: identical `201` body with a random-looking `leadId`; nothing stored.

### 2.3 Error response

```json
{ "ok": false, "code": "validation_failed", "message_key": "leads.error.validation_failed",
  "fields": { "email": "leads.field.email_invalid" }, "retryable": false,
  "fallback": { "whatsapp": true, "phone": true } }
```
`fields` only on validation errors (field → i18n key). `fallback` is present on every `5xx` and on `verification_unavailable`-type errors so the UI always offers WhatsApp/phone. The server never echoes submitted values.

| HTTP | `code` | When | `retryable` | Client action |
|---|---|---|---|---|
| 400 | `invalid_json` | body not JSON or wrong content type | no | bug; show generic error |
| 400 | `validation_failed` | zod failed; `fields` filled | no | show field errors |
| 403 | `origin_not_allowed` | `Origin`/`Sec-Fetch-Site` not our site | no | generic error |
| 403 | `captcha_failed` | Turnstile token **invalid, expired, reused, or missing** | yes (get a new token) | reset widget, ask to retry |
| 405 | `method_not_allowed` | other verbs | no | — |
| 413 | `payload_too_large` | body > 16 KB | no | — |
| 415 | `unsupported_media_type` | not `application/json` | no | — |
| 429 | `rate_limited` | limit exceeded (§5); `Retry-After` header | yes after wait | show wait message |
| 500 | `internal_error` | unexpected | yes | show fallback contacts |
| 503 | `verification_unavailable` | Turnstile unreachable and the unverified circuit breaker is open (section 4) | yes | show WhatsApp/phone fallback |
| 503 | `storage_unavailable` | DB commit failed or unavailable | yes | keep form data, show fallback contacts |
Turnstile unreachable is normally accepted as `unverified` (section 4); `verification_unavailable` only appears when the circuit breaker is open.

## 3. Pipeline (sequence)

```mermaid
sequenceDiagram
  participant B as Browser form
  participant A as POST /api/leads
  participant T as Turnstile siteverify
  participant D as PostgreSQL
  participant W as Worker (cron + after())
  participant X as Email / Chat / CRM
  B->>A: JSON + turnstileToken + idempotencyKey
  A->>A: origin, size, JSON, honeypot, zod
  A->>D: idempotency lookup
  A->>D: rate-limit counter (ip hash)
  alt already stored
    A-->>B: 200 same body (replay)
  else new
    A->>T: verify token (timeout 3 s)
    alt valid / unreachable
      A->>D: BEGIN; insert lead; insert 3 leadJobs; COMMIT
      A-->>B: 201
      A--)W: after(): best-effort first attempt
      W->>D: claim due jobs (FOR UPDATE SKIP LOCKED)
      W->>X: send email / chat / CRM
      W->>D: mark sent or schedule retry
    else invalid
      A-->>B: 403 captcha_failed
    end
  end
```

### 3.1 Step order (final)

| # | Step | On failure |
|---|---|---|
| 1 | Method, `Content-Type`, body size ≤ 16 KB, `Origin` / `Sec-Fetch-Site` same-site | 405 / 415 / 413 / 403 |
| 2 | Parse JSON | 400 `invalid_json` |
| 3 | **Honeypot** (`contact_ref_hp` non-empty) | fake `201`, nothing stored, counted for abuse stats (no PII) |
| 4 | zod parse (`leadSchema`) | 400 `validation_failed` |
| 5 | **Idempotency lookup** by `idempotencyKey` (before rate limit, so a legitimate retry gets the replay and not a 429; before Turnstile, because tokens are single use) | replay `200` |
| 6 | **Rate limit** (DB counter, §5). Replays are not counted | 429 |
| 7 | **Turnstile siteverify** (§4) | invalid → 403; unreachable → continue as `unverified` |
| 8 | **Transaction**: insert `leads` + three `leadJobs` rows (email, chat, crm; crm omitted when unverified) | 503 `storage_unavailable`, nothing acknowledged |
| 9 | Respond `201` | — |
| 10 | `after()` best-effort: try the new jobs once now | failures are only logged; cron worker owns retry |

Hritik's nits applied: idempotency before rate limit and Turnstile; rate limit before the Turnstile call; honeypot returns a normal-looking `201`; insert and jobs in one transaction.

## 4. Turnstile

- Widget (managed mode) on every public form; site key is public `NEXT_PUBLIC_TURNSTILE_SITE_KEY`; secret `TURNSTILE_SECRET_KEY` server only.
- Server calls Cloudflare `siteverify` with `secret`, `response`, `remoteip` (optional) and an `idempotency_key` per token. Timeout **3 s**, no retry in-request.
- Outcomes:

| Outcome | Result |
|---|---|
| `success: true` | `verification = verified`. Full pipeline |
| `success: false` (invalid, expired, duplicate, missing token) | `403 captcha_failed`, nothing stored |
| Timeout, network error, HTTP 5xx from Cloudflare | **PM decision (2026-11-06):** do not fail closed. Store lead with `verification = unverified-turnstile-unavailable`, **skip the CRM job**, send email and chat alerts with a visible "Spam check unavailable" flag, sales triages in admin (status `new`, filter by verification). Log event `turnstile_unreachable` (no PII) and count it; an alert fires if more than 5 per hour |
**Guardrails for the unverified path (PM + Hritik, 2026-11-06):**
1. Unverified leads are marked in admin (filter and red badge on `verification`) and flagged in email, chat and digest.
2. Lower cap per IP hash while unverified: 2 per hour and 5 per 24 h (normal limits in section 5 still apply on top).
3. **Circuit breaker:** global counter of stored unverified leads per rolling hour. Proposed **N = 20 per hour** (TODO(roshan) confirm N). Above N, the API stops storing unverified leads and returns `503 verification_unavailable` (`retryable: true`, `fallback: { whatsapp, phone }`) so the visitor is sent to WhatsApp or phone. The breaker closes automatically when Turnstile verifies again or the hour rolls over. Rationale: real enquiries survive a Cloudflare outage, a bot flood during an outage cannot fill the database or the sales inbox.
4. Metrics (structured log, no PII) `turnstile_unreachable` and `unverified_lead_stored`, plus `circuit_breaker_open`; Raj alerts on them (more than 5 unreachable per hour, or breaker open).
Note: step 5 rate limit, zod and honeypot still apply, so abuse during a Cloudflare outage is bounded by the per-IP limits. An `unverified` lead can be promoted by sales; the CRM job is then created manually (admin action "Push to CRM").
- Hostname check: response `hostname` must equal the site host (or a configured allowlist for staging) else treated as invalid.
- Test keys: Cloudflare publishes dummy site/secret keys for local and CI; Raj adds them to the CI env (names only below).

## 5. Rate limiting

DB-backed counters (table `leadRateLimits`: `keyHash`, `windowStart`, `count`) so limits survive restart and work across overlapping containers. Key = `sha256(IP + IP_HASH_SALT)`; the raw IP is never stored or logged. `IP` comes from `CF-Connecting-IP` (trusted only when the request came through Cloudflare; Raj configures the trusted proxy setting).

| Limit | Value (proposal) |
|---|---|
| Per IP hash | 5 requests / 10 min and 20 / 24 h |
| Global safety valve | 300 requests / hour (returns 429 and raises a Sentry event) |
| Same email or phone | 3 stored leads / 24 h; the 4th returns `201` replay-style without a new row (avoids revealing the limit). A counter `repeat_contact_suppressed` is logged and listed in the daily digest so sales sees repeat contact attempts |
Cloudflare WAF rate-limit rule on `/api/leads` is the first line (Raj, T-50x); these app limits are the second. Expired counter rows are deleted by the worker daily. `IP_HASH_SALT` rotation and the retention period are **TODO(roshan)**.

## 6. Outbox and retry

### 6.1 Table `leadJobs` (hidden collection, §3.17 of content model)
`id, lead (FK), channel (email|chat|crm), status (pending|sending|sent|failed|dead), attempts, nextAttemptAt, lockedAt, lastError, sentAt`. Holds the lead id only. The worker loads the lead at send time (no PII copy in the outbox).
One job per (lead, channel) enforced by a unique index. CRM job absent for `unverified` leads.

### 6.2 State machine
`pending → sending → sent` or `sending → failed (attempts+1, nextAttemptAt set) → sending …` and after the last attempt `dead`.

| Attempt | Delay after previous failure |
|---|---|
| 1 | immediately (best effort in `after()`, else next cron tick) |
| 2 | 1 min |
| 3 | 5 min |
| 4 | 30 min |
| 5 | 2 h |
| 6 | 12 h |
| then | `dead` (stop) |
Jitter ±20%. `Retry-After` from a provider is respected when longer. Permanent errors (HTTP 400/401/403/404 from provider, invalid recipient) skip retries and go `dead` at once with the reason in `lastError` (and a Sentry event without PII).

### 6.3 Worker
- Route `POST /api/internal/lead-worker` (Neha). Protected by header `x-worker-secret` = `WORKER_SECRET` (constant-time compare); not listed in sitemap; `no-store`; blocked by Cloudflare for public traffic except the VPS scheduler (Raj). Runs every minute from a VPS cron/systemd timer or Docker scheduler container (Raj).
- Claims up to 20 due jobs: `UPDATE leadJobs SET status='sending', lockedAt=now() WHERE id IN (SELECT id FROM leadJobs WHERE status IN ('pending','failed') AND nextAttemptAt <= now() ORDER BY nextAttemptAt LIMIT 20 FOR UPDATE SKIP LOCKED) RETURNING *`. Overlapping runs cannot double-send.
- A job stuck in `sending` longer than 5 min (crash) is reset to `failed` at the start of each run.
- Per-run time limit 50 s; remaining jobs wait for the next tick.
- **Idempotent sends:** email passes the provider idempotency key `lead:<id>:email`; Slack/chat has no idempotency, so the job writes `sent` immediately after the provider 2xx; the tiny crash window can duplicate one chat alert (acceptable, never loses). CRM uses upsert by email (§9).
- **Dead letters:** admin sees a red per-channel status on the lead. A daily digest email (08:00 NPT) to the sales address lists leads with any `dead` or `failed` job older than 1 h and any `unverified` lead still `new`. Admin action "Retry" resets attempts.
- **Fallback alert path:** if the email job for a lead is `dead`, the worker raises one Sentry event (lead id only) so Roshan/Raj notice even when all channels fail.

### 6.4 Transaction requirement (to verify in week 2)
Payload local API must run lead insert and `leadJobs` inserts with the same `req.transaction`. If it cannot, the insert is done with Drizzle in `lib/server/leads/store.ts` (Hritik agreed). Spike: Mon 16 Nov.

## 7. Failure matrix (ADR-007)

| Failure | Visitor sees | Lead stored? | What happens next |
|---|---|---|---|
| Email provider down / 5xx | success | yes | email job retries per §6.2; chat and CRM unaffected |
| Chat webhook down | success | yes | chat job retries; email still sent |
| CRM down / rate limited | success | yes | CRM job retries; sales already alerted |
| All three down | success | yes | all jobs retry up to ~15 h then `dead`; digest + Sentry alert; admin shows red status; sales reads leads in admin |
| Worker not running (cron broken) | success | yes | `after()` first attempt still tries once; uptime check on worker heartbeat (`/api/health` reports oldest due job age; Raj alerts if > 10 min) |
| App crashes after commit, before response | client retry with same key | yes | replay `200`; jobs picked up by cron |
| App crashes before commit | retry succeeds later | no (not acknowledged) | client retries with same `idempotencyKey` |
| DB unavailable | error + WhatsApp/phone fallback | no (not acknowledged) | `503 storage_unavailable`; Sentry event; form keeps data |
| Turnstile token **invalid / missing / reused** | "please retry" + widget reset | no | `403 captcha_failed` |
| Turnstile service **unreachable** (timeout/5xx) | success | yes, `verification = unverified-turnstile-unavailable` | no CRM job; alerts flagged "Spam check unavailable"; stricter per-IP cap (2/h); sales triages; metric alert if > 5/h |
| Turnstile unreachable and unverified count > N/h (circuit breaker) | error + WhatsApp/phone fallback | no (not acknowledged) | `503 verification_unavailable`; breaker closes when Turnstile recovers or hour rolls |
| Rate limited | wait message | no | `429 + Retry-After`; fallback contacts shown |
| Honeypot | success (fake) | no | counted |
| Duplicate submit (double click, retry) | success | one lead only | `200` replay |
| Browser closes before response | none | maybe | if committed, lead exists and alerts go; otherwise visitor can use WhatsApp |

## 10. Privacy and security

- Consent (`consent.contact === true`) is mandatory; the form shows the privacy link (`/privacy`) and stores `consentAt` and `policyVersion` (from `pages.legalVersion`). Marketing opt-in is **not** collected here.
- Stored PII: name, email, phone, company, message, `ipHash` (salted), truncated user agent. Raw IP, full user agent and Turnstile token are not stored.
- Retention and deletion procedure: **TODO(roshan)**. Technical support: admin "Anonymise lead" action (blanks PII, keeps counts and source) and a documented export/delete on request.
- Logs: structured, lead `publicId` only. Never log name, email, phone, message, IP, tokens, provider responses containing recipient addresses. Sentry `beforeSend` scrubs request bodies, headers, cookies, user data (Raj + Hritik in `sentry.*.config.ts`).
- Email templates escape all values; chat messages escape markdown/mention characters (`@channel`, `<!here>`).
- Headers on the route: `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`. CORS: none (same origin). CSRF: not cookie-authenticated; origin check in step 1 plus Turnstile.
- Payload REST for `leads` is closed to the public; only server code creates leads.
- **Data processors:** the email provider, the chat tool and the CRM each receive lead PII, so each is a data processor. Each must be named in the privacy policy (Sudip / PM) and each account needs Roshan's written approval before creation (CLAUDE.md §3).
- Secrets: env vars only (§11); read via `src/lib/env.ts` (server schema).

## 12. Adapter interfaces (`src/lib/server/leads/`)

```ts
interface Channel<TLead = LeadRecord> {
  name: 'email' | 'chat' | 'crm'
  send(lead: TLead, ctx: { idempotencyKey: string }): Promise<
    { ok: true; externalId?: string } |
    { ok: false; retryable: boolean; reason: string } // reason: provider code, no PII
  >
}
```
Files: `pipeline.ts` (orchestration), `store.ts` (transaction), `turnstile.ts`, `rate-limit.ts`, `worker.ts`, `channels/{email,chat,crm}.ts` with `resend|brevo|slack|telegram|hubspot|log` implementations, `templates.ts`. Expected failures return typed results, unexpected ones throw (standards §3).

## 13. Contract for the form (Mahendra)

1. Generate `idempotencyKey` (`crypto.randomUUID()`) when the form mounts; keep it for retries; regenerate only after a successful `201`.
2. UTM values are read from the landing URL on first page view and kept in `sessionStorage` (first-party, no third party involved), then sent in `source`. ASSUMPTION: first-party UTM capture before consent is allowed. TODO(roshan): confirm (ADR-006 / privacy), see open question 8.
3. Render the Turnstile widget; send a fresh token with each submit; on `403 captcha_failed` reset the widget.
4. Honeypot field named `contact_ref_hp` (import `HONEYPOT_FIELD`; `website` is autofilled by browsers), visually hidden, `tabindex=-1`, `autocomplete=off`, `aria-hidden`.
5. Client uses the same `leadSchema` for validation; server errors map `fields` keys to UI messages in `src/messages/`.
6. On `201` or `200` replay: fire analytics conversion event (after consent) with `formKind`, `service`, `utm`; then navigate to `next.redirect`.
7. On `5xx` or network error: keep entered data, show message plus WhatsApp and phone fallback; allow retry with the same key.
8. All error texts come from message keys; no raw server text shown.
